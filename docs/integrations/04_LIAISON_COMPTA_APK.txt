COMPTAFLOW — LIAISON COMPTA-APK
SPECIFICATION FONCTIONNELLE ET TECHNIQUE — CIBLE À IMPLÉMENTER

OBJECTIF
Centraliser dans le SuperAdmin de COMPTAFLOW l'enregistrement, l'authentification,
les droits et les liaisons de toutes les applications qui déposent des données.
Aucune modification du code source ni ajout manuel d'un secret dans le .env ne doit
être nécessaire à chaque nouvelle application ou entreprise.

MENU SUPERADMIN
Créer une rubrique principale « Liaison COMPTA-APK » avec deux entrées cliquables :

1. APPLICATION MAISON — LA SUITE FLOW
   - Liste des applications internes autorisées : SELFLOW, RH-FLOW, etc.
   - Liste des liaisons de chaque application.
   - Liste des entreprises COMPTAFLOW disponibles pour une liaison maison.
   - Action « Lier à une entreprise existante ».
   - Action « Créer une entreprise et lier » si le parcours métier le permet.
   - Une application maison ne voit que les entreprises et les liaisons prévues
     pour son périmètre ; les accès sont contrôlés côté serveur.

2. APPLICATION EXTERNE
   - Liste des applications tierces enregistrées (nom, propriétaire, statut).
   - Création et modification d'une application externe.
   - Création d'une entreprise COMPTAFLOW dédiée à cette application.
   - Génération, renouvellement, révocation et date d'expiration des identifiants.
   - Historique des connexions et des dépôts.
   - Une application externe ne reçoit JAMAIS la liste globale des entreprises
     COMPTAFLOW et ne peut pas choisir un company_id librement.

MODELE DE SECURITE CIBLE
- Chaque application enregistrée possède un identifiant client (client_id).
- COMPTAFLOW génère un secret client aléatoire (client_secret) ; il est affiché
  une seule fois à la création ou au renouvellement.
- Le secret n'est jamais commité dans un dépôt, écrit en dur dans le code,
  transmis dans le JSON métier ou journalisé.
- COMPTAFLOW conserve uniquement une empreinte vérifiable du secret.
- Chaque liaison associe une application à un ou plusieurs dossiers explicitement
  autorisés selon son type (maison ou externe).
- Le contexte entreprise est résolu côté serveur depuis l'identité authentifiée
  et la liaison active, jamais depuis un company_id fourni librement dans le JSON.
- Autorisations distinctes par famille : referentiel, écritures, pièces justificatives.
- Révocation immédiate, rotation de secret, limitation de débit, journalisation,
  protection anti-rejeu et idempotence.
- Les secrets nécessaires à l'appel sont enregistrés dans l'interface de
  configuration de l'application cliente, avec stockage chiffré côté client.
  Aucun changement de code ni édition manuelle du .env pour chaque liaison.
- Le secret global historique EXTERNAL_SYNC_SECRET est un mécanisme transitoire.
  Il doit être retiré des appels métier après migration contrôlée vers les
  identifiants applicatifs. Ne pas le supprimer avant que les clients actifs
  aient migré et que les routes soient testées.

AUTHENTIFICATION HTTP CIBLE
Authorization: Bearer <jeton applicatif>
Le jeton est délivré/renouvelé par COMPTAFLOW à partir des identifiants applicatifs.
Ne pas envoyer client_secret, secret ou numéro d'entreprise dans le payload métier.
X-Company-Key peut rester temporairement accepté pour compatibilité historique,
mais ne doit pas remplacer l'autorisation applicative ni permettre de changer
d'entreprise. Le contrat final doit choisir un seul mécanisme cohérent et documenté.

PARCOURS MAISON
1. Le SuperAdmin sélectionne SELFLOW ou RH-FLOW.
2. Il consulte les entreprises COMPTAFLOW autorisées à être liées.
3. Il lie l'entreprise existante ou crée un dossier depuis le parcours autorisé.
4. COMPTAFLOW crée une liaison explicite et génère les paramètres d'accès.
5. L'application cliente reçoit/configure ces paramètres depuis son écran sécurisé.
6. Les endpoints de consultation et de dépôt ne renvoient que les données du dossier lié.

PARCOURS EXTERNE
1. Le SuperAdmin enregistre l'application et son propriétaire.
2. Il crée le dossier COMPTAFLOW dédié à cette intégration.
3. COMPTAFLOW crée une liaison unique et des identifiants propres à cette application.
4. Le propriétaire reçoit les identifiants une seule fois par un canal sécurisé.
5. L'application externe ne peut ni lister les autres dossiers ni se rattacher elle-même
   à une autre entreprise.

ENDPOINTS ET DEVERSEMENTS
Les endpoints restent la seule porte d'entrée. Aucun accès SQL ou écriture directe
dans les tables COMPTAFLOW depuis SELFLOW, RH-FLOW ou une application externe.
Les familles de données sont :
- référentiel : plan comptable, tiers, codes journaux ;
- écritures comptables : ventes, achats, OD, paie, stock et autres opérations ;
- pièces justificatives : dépôt PDF lié à une opération précise.

ÉTAT AU 19/11/2026 : les routes de déversement référentiel, écritures et regroupement
sont protégées par cle.entreprise ; les contrôleurs n'exigent plus le secret global ni
les identifiants de société dans les payloads métier. SELFLOW envoie ces payloads
sans secret ni identifiants de routage. Cela ne constitue PAS encore l'authentification
applicative centralisée décrite ici : les écrans SuperAdmin, tables d'applications,
client_id/client_secret, jetons Bearer et permissions par application restent à réaliser.

NUMEROS ORIGINAUX
L'application source transmet uniquement son numéro métier courant.
Exemple : numero_de_compte = "401000".
COMPTAFLOW conserve cette valeur comme numero_original et génère son propre
numero_de_compte selon les paramètres du dossier. L'application source ne transmet
jamais un deuxième champ numero_original.
Même principe pour les numéros de tiers et les codes journaux. Les écritures
peuvent ensuite retrouver les référentiels grâce à ces numéros source stables.

IDENTIFIANTS DANS LE CORPS JSON
Ne pas demander comptaflow_company_id ni selflow_company_id pour déterminer le
dossier destinataire des écritures. Le dossier est déterminé par la liaison
authentifiée côté serveur. Les identifiants source utiles à l'idempotence peuvent
rester dans le payload (cle_source, operation_source), sans servir à choisir le dossier.

MIGRATION ET COMPATIBILITE
- Inventorier toutes les routes qui lisent EXTERNAL_SYNC_SECRET, secret dans le corps
  ou X-Sync-Secret.
- Introduire les tables et modèles d'applications, secrets hashés et liaisons.
- Créer middleware d'authentification applicative et résolution du dossier lié.
- Créer les écrans SuperAdmin et leurs politiques d'accès.
- Migrer les connecteurs SELFLOW et RH-FLOW vers la configuration sécurisée.
- Garder une période de compatibilité contrôlée, puis retirer l'ancien secret global.
- Tester les cas : application maison liée à plusieurs dossiers, externe isolée,
  secret invalide, révocation, rotation, accès croisé interdit, rejeu idempotent,
  et dépôt dans le mauvais dossier refusé.

ETAT
Ce fichier est une spécification de réalisation. L'interface « Liaison COMPTA-APK »,
les tables d'applications, le mécanisme d'authentification applicative et la migration
des endpoints ne sont pas encore déclarés livrés par la seule présence de ce document.


ETAT D'AVANCEMENT COMPLEMENTAIRE — 19/11/2026

  Il réaffecte les anciennes lignes vers le nouvel identifiant de plan comptable
  et met à jour les comptes généraux des tiers ; aucun montant n'est recalculé.
  SELFLOW synchronise d'abord le référentiel puis met cette propagation en file.

  mois ; le quotidien reste optionnel. La date de fin est facultative et les
  périodes sont traitées après leur échéance.
- SELFLOW : les payloads référentiel et écritures n'envoient plus le secret global,
  les identifiants de société ni un champ numero_original séparé.
- RESTE A REALISER : interface SuperAdmin « Liaison COMPTA-APK » avec les deux
  sections « APPLICATION MAISON : LA SUITE FLOW » et « APPLICATION EXTERNE »,
  registre des applications, liaisons, permissions, génération/rotation/révocation
  centralisées des identifiants applicatifs et jetons. L'envoi PDF SELFLOW est
  maintenant intégré au job de déversement des opérations. RH-FLOW reste hors développement ici :
  seul le contrat de données lui est fourni.


IMPLEMENTATION DU PARCOURS SIMPLIFIE — 20/11/2026

APPLICATIONS MAISON
- COMPTAFLOW stocke l'URL de l'application et génère un code aléatoire de liaison, affiché une seule fois, valable 30 jours.
- POST /api/integration/pairing/redeem reçoit pairing_code et application_code. L'échange est à usage unique et retourne client_id/client_secret ; le secret est haché en base.
- Pour afficher les entreprises partenaires, l'application distante doit exposer GET /api/integration/companies, protégé par X-Integration-Pairing-Code, et répondre :
  { "data": [ { "id": "identifiant-source", "name": "Nom entreprise" } ] }
- L'écran COMPTAFLOW choisit d'abord le dossier local, puis charge ce catalogue dans une fenêtre. Le serveur vérifie à nouveau l'identifiant et le nom sélectionnés avant d'enregistrer la liaison.
- La correspondance distante est stockée dans integration_application_companies.partner_company_id / partner_company_name.
- Le code manuel est renouvelable. Le renouvellement automatique n'est pas activé : il exige un protocole de renouvellement confirmé par les deux applications afin de ne pas couper la liaison.

APPLICATIONS EXTERNES
- POST /api/integration/external/company-requests reçoit client_id, client_secret, request_id, company_name, manager_name, manager_email, activity, legal_form, phone_number.
- La demande est idempotente par application + request_id. Aucun company_id n'est accepté dans la demande.
- Le Super Admin examine la file, renseigne les dates de l'exercice, puis accepte ou rejette.
- Après acceptation, COMPTAFLOW crée le dossier dédié, l'exercice et la liaison. Le gérant reçoit un lien d'activation temporaire pour choisir son propre mot de passe.
- POST /api/integration/external/company-requests/{requestId}/status, avec client_id/client_secret dans le corps, permet à l'application de consulter uniquement sa propre demande et de récupérer le company.id après acceptation.
- L'application externe ne reçoit aucune liste globale et ne peut pas choisir un dossier existant.

AUDIT
- Les événements API authentifiés conservent la méthode HTTP, durée, identifiant de requête, route, IP, payload et réponse avec masquage des champs sensibles.
- Les mots de passe, secrets, tokens, clés et en-têtes d'authentification ne doivent jamais apparaître en clair dans les journaux.

LIMITES DE LIVRAISON
- Le code RH-FLOW n'est pas dans le dépôt COMPTAFLOW. Son endpoint GET /api/integration/companies et son bouton Déverser restent à réaliser/tester dans RH-FLOW.
- Le bouton Déverser appartient à l'application source : il doit déclencher l'appel POST vers les endpoints métier COMPTAFLOW existants, et non provoquer un transfert automatique lors de la création de la liaison.
